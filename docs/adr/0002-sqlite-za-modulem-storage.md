## Контекст

Данные заявок, состояния диалогов и настройки не должны пропадать при перезапуске сервиса. Хостинг даёт постоянный диск, а базы-сервера на бесплатном тарифе нет.

## Решение

Всё постоянное состояние лежит в одной базе SQLite на диске хостинга: настройки, переопределённые тексты, сессии диалогов, заявки, сферы и примеры работ, обработанные идентификаторы апдейтов, неудачные попытки входа в панель. SQL знает только модуль `storage`; остальной код работает через его методы и не видит ни таблиц, ни сериализации.

## Почему

- Postgres отвергнут для демо: отдельный сервер, которого нет на бесплатном хостинге, и лишняя настройка ради одного заказчика. Граница `storage` оставлена, чтобы замена затронула один модуль.
- Хранение сессий в памяти процесса отвергнуто: перезапуск сервиса обрывал бы начатые анкеты, а это прямое требование брифа.
- Отдельные хранилища под разные данные (файл для настроек, база для заявок) отвергнуты: одна транзакционная база проще бэкапить и проверять тестом «новый движок на той же базе».

## Последствия

- Для продакшна SQLite — временный выбор: по 152-ФЗ база с персональными данными граждан РФ должна храниться в РФ, а PythonAnywhere этого не гарантирует. Это записано в отчёте как риск, а не решено.
- Заявки с телефонами и именами лежат файлом на диске хостинга; резервного копирования у демо нет.
- Одна запись на одного писателя: параллельные записи при росте нагрузки станут узким местом, WAL смягчает, но не убирает это.
- Миграции схемы делаются только как `CREATE TABLE IF NOT EXISTS` при старте; изменение существующих таблиц придётся писать вручную.
- Любой SQL вне `storage` ломает границу; это проверяется только дисциплиной ревью.
