## Контекст

Заказчик должен сам, без программиста, менять тексты, контакты, информационные блоки и примеры работ, и видеть правку в боте без правки кода.

## Решение

Значения по умолчанию всех текстов лежат в коде, правки из панели хранятся в базе, бот читает базу на каждом апдейте. Тексты из панели — простой текст: бот экранирует всё, что отправляет, сам выделяет заголовок вопроса жирным, а подставляет только имя клиента в финальном сообщении. Каждая строка, которую видит клиент, берётся из каталога текстов по ключу; в движке таких строк нет.

## Почему

- Тексты только в коде отвергнуты: любая правка требует программиста и деплоя, что противоречит условию брифа.
- Тексты только в базе без значений в коде отвергнуты: новая база была бы пустой, «Вернуть по умолчанию» было бы нечем выполнить, а проверку «все тексты из PDF на месте» нечем делать.
- Кэш текстов в памяти с перезапуском отвергнут: правка должна быть видна со следующего сообщения, а перезапуск на хостинге — действие заказчика.
- Разрешить разметку HTML из панели отвергнуто: неверный тег ломает отправку сообщения, а клиент мог бы внедрить разметку через подстановку.
- Богатые шаблоны (больше одной подстановки) отвергнуты: простая замена безопаснее и достаточна для единственной переменной.

## Последствия

- Каждый апдейт делает чтение переопределений из базы; на SQLite это дёшево, но это постоянная нагрузка.
- Заказчик не может ни выделить слово, ни вставить ссылку в текст: форматирование недоступно.
- Две кнопки из PDF длиннее 60 символов, поэтому лимит кнопки в панели — большее из 60 и длины значения по умолчанию; это исключение надо помнить при проверках.
- Ключ текста стал публичным контрактом: переименование ключа молча сбросит правку заказчика к значению по умолчанию.
- Эмодзи в значениях по умолчанию подобраны по смыслу, потому что при извлечении из PDF они потерялись.
